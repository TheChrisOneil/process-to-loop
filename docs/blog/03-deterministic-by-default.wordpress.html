Auditable Workflows in a Regulated Environment, Part 3 of 4.

A rule written into a prompt costs tokens on every run, for the life of the workflow. The same rule written in code costs nothing after it ships. It also returns the same answer every time.

Most teams still write their business rules as prompts.

I built a design format that makes that mistake hard to commit. It is the core of the proprietary context I described in Part 1. A model writes the design. Deterministic tooling validates it, renders it, and compiles it. This post explains the constraints that make the format work and how each one protects either TCO or TVR.

Readable by a process owner. Parseable by a script. Writable by a model.

The format is plain text, organized in sections that open with an @ name. I rejected JSON because the process owner must read and own the logic. A clinic manager can read a pipe-delimited table. Few can read nested braces.

Every design begins with the unit of work: the smallest thing that receives one decision. The design classifies that decision with the two people test. If two competent people, unable to confer, would produce the same answer, the decision is a rule and belongs in code. If they would differ, it is judgment, and the design must name what checks it. A design declares exactly one judgment per unit. Everything else is a rule.

Each step carries a type and an actor, and the validator forces them to agree. Coordination, mechanical, test, and gate steps always run as code. Only a thinking step may use a model or a human. That single constraint keeps the inference line on the TCO ledger small and visible.

A condition without a number, a comparison, or the word "never" is a suggestion.

Gates are where a workflow refuses. Every gate condition must contain a number, a comparison, or the word "never." Every refusal message must name the next human action in at least 25 characters. The validator rejects placeholders such as "needs review" or "escalate." A refusal that tells nobody what to do is a stalled queue, and stalled queues destroy TVR.

A gate written in prose compiles to a stub somebody must implement. A gate backed by a decision table compiles to working logic. Tables answer three questions that conditionals hide: does any input fall through, do two rules claim the same input, and does any output never occur? Under the unique hit policy the validator proves no two rules overlap. A case that matches no rule is a refusal. The workflow never invents a default, because inventing an answer is the guess this system exists to prevent.

A design may narrow a tool's permissions. It may never widen them.

Healthcare adds a boundary. Every data source comes from a catalog that declares its data class. A design inherits the catalog's permissions and may only narrow them. A tool carrying protected health information may feed a model step only when the catalog records a business associate agreement covering that model provider, with a current attestation date. A lapsed attestation refuses the design. The validator enforces that rule before anyone signs. The policy lives in the catalog because it changes when a contract changes.

Assumptions carry provenance. Each one cites the interview question it answers and states how it was answered: stated by the process owner, unanswered and assumed, or delegated to the system by the owner. An auditor reading 44 assumptions must be able to separate a confirmed fact from a surviving guess. The validator refuses a design that flattens the three into one voice.

A TVR baseline nobody measured is written "unmeasured." It is never estimated.

This is where TVR enters the development loop. Every design must declare at least three KPIs with a baseline: one for cost, one for quality, and one for Total Value Realized. The TVR kinds map to four value vectors: velocity at the client touchpoint, throughput per existing reviewer, organizational speed, and margin recovered per unit net of compute. A baseline nobody has measured is written as unmeasured. The validator accepts it with a warning. It refuses an invented number.

Two more constraints close the loop. Evidence must be written by a mechanical step, so the component that makes a claim never writes its own proof. A record section declares where every state change is appended, where each unit's outcome lands, how long records are kept, and where the approval signature lives. A workflow that records nothing cannot be audited.

The format makes the model's job narrow. It drafts one artifact. Rules, refusals, permissions, and value targets are checked by code before a human signs. Part 4 covers what happens between the draft and the signature: an audit by a different model [1].
